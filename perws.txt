# Анализ ТЗ: AI-система управления недвижимостью

## 1. Архитектура MVP

### Что входит в первый этап (из п.16 ТЗ)

```
┌─────────────────────────────────────────────────────┐
│                  Веб-приложение                      │
│  (React/Next.js — дашборд + AI-чат + карточки)       │
├─────────────────────────────────────────────────────┤
│              API Gateway (FastAPI)                   │
├──────────┬──────────┬──────────┬───────────────────┤
│ Каталог  │ Документы│ Аналитика │  AI-оркестратор   │
│ объектов │  (OCR +  │ (финансы)│  (роутинг запросов)│
│ арендат. │  LLM)    │          │                    │
│ договоров│          │          │                    │
├──────────┴──────────┴──────────┴───────────────────┤
│   PostgreSQL (основные данные) + pgvector (эмбеддинги)│
│   S3/MinIO (документы, фото)                        │
│   Bitrix24 (задачи, CRM) — через REST API + вебхуки │
└─────────────────────────────────────────────────────┘
```

**БД — PostgreSQL.** Таблицы: `objects`, `tenants`, `contracts`, `payments`, `documents`, `tasks_sync`, `users`, `audit_log`. Для RAG по документам — `pgvector` (не нужен отдельный векторный БД).

**Backend — Python + FastAPI.** Причины: лучший стек для AI/LLM, async, быстрая разработка, много библиотек для работы с документами.

**Frontend — React/Next.js.** Дашборд с виджетами (финансы, объекты, задачи) + панель AI-чата справа/слева.

## 2. AI-анализ договоров (самая технически сложная часть)

### Пайплайн

```
PDF/Word загрузка
    ↓
OCR + извлечение текста (pdfplumber / python-docx / Tesseract для сканов)
    ↓
Чанкование по разделам/пунктам
    ↓
Извлечение структурированных данных (LLM + function calling)
    → {тип, стороны, сроки, стоимость, индексация, штрафы, ...}
    ↓
Анализ рисков (LLM с промптом-чеклистом + эталонный шаблон)
    ↓
Результат: 🟢/🟡/🔴 со ссылками на пункты
    ↓
Сохранение в БД + создание задач в Bitrix24
```

### Ключевое решение

Нужен **эталонный шаблон** договора по каждому типу (аренда, продажа). LLM сравнивает загруженный договор с эталоном и находит отклонения.

### Промпт-инжиниринг

Структурированный промпт с чеклистом из 15 пунктов (как в п.4 ТЗ), на выходе — JSON с категоризацией риска.

### Для сканов плохого качества

Yandex Vision OCR или Tesseract + постобработка.

## 3. Выбор LLM и контур данных

Это критическое решение. ТЗ подразумевает работу с коммерческой тайной и персональными данными → **152-ФЗ**.

| Модель | Плюсы | Минусы |
|--------|-------|--------|
| **YandexGPT** | 152-ФЗ, РФ-хостинг | Ограниченный function calling |
| **GPT-4o (OpenAI)** | Лучшее качество анализа | Данные уходят за рубеж (нужны меры) |
| **Локальная LLM** (Llama/Qwen на GPU) | Полный контроль данных | Нужен GPU-сервер, ниже качество |

### Рекомендация: гибридный подход

- **Локальная Qwen 2.5 72B** (если есть GPU) для анализа документов — данные не уходят
- **GPT-4o** через прокси с маскированием персональных данных (деперсонализация перед отправкой)
- При необходимости — **YandexGPT** для обработки персональных данных (152-ФЗ compliant)

**Хранение данных:** on-premise сервер или приватное облако в РФ (Yandex Cloud / Selectel).

## 4. Интеграция с Bitrix24

### Что маппить

| Наша система | Bitrix24 |
|-------------|----------|
| Задачи | `tasks.task` (REST API) |
| Арендаторы | CRM `company` или `contact` |
| Сделки (продажа/аренда) | CRM `deal` |
| Объекты | CRM `item` (умные процессы) |
| Сотрудники | `user.get` |
| Документы | `disk.storage` / `document` |
| Активности | `calendar.event` / `task.commentitem` |

### Механика

- REST API (входящий вебхук) для создания/чтения задач
- Исходящие вебхуки (события `ontaskupdate`, `oncrmdealupdate`) для синхронизации обратно
- Двусторонняя синхронизация через очередь (Redis + фоновый worker)

**AI создаёт задачу** → POST `/rest/tasks.task.add` → получает ID → сохраняет связь в нашей БД → отслеживает статус.

## 6. Multi-agent архитектура

### Может ли один агент справиться?

**Коротко — нет.** Это не задача одного агента. Нужна **мульти-агентная система с оркестратором**.

### Почему не один агент

- Разные домены знаний (документы, финансы, рынок, задачи)
- Разные инструменты (OCR, БД, Bitrix24, внешние API)
- Разные промпты и модели (для документов нужен GPT-4, для уведомлений — проще)
- Разграничение доступа

### Рекомендуемая архитектура

```
                    ┌─────────────────┐
                    │  AI-ДИРЕКТОР    │  ← Собственник
                    │  (оркестратор)  │
                    └────┬────┬───────┘
                         │    │
          ┌──────────────┼────┼──────────────┐
          ▼              ▼    ▼              ▼
  ┌──────────────┐ ┌──────────┐ ┌──────────┐ ┌─────────────┐
  │ Документный  │ │Финансо-  │ │Рыночный  │ │ Операционный│
  │  агент       │ │вый агент │ │  агент   │ │   агент     │
  │              │ │          │ │          │ │             │
  │ OCR, анализ  │ │Доходы,   │ │Цены,     │ │Задачи,      │
  │ рисков,      │ │расходы,  │ставки,    │ │контроль,    │
  │ сравнение с  │ │доходность│аналоги    │ │уведомления  │
  │ эталоном     │ │          │ │          │ │             │
  └──────┬───────┘ └────┬─────┘ └────┬─────┘ └──────┬──────┘
         │              │           │              │
         ▼              ▼           ▼              ▼
  ┌──────────────────────────────────────────────────────┐
  │          Инструменты (Tools / Function Calling)       │
  │  search_objects │ get_finances │ create_bitrix_task  │
  │  analyze_doc    │ calc_yield   │ get_market_data     │
  │  get_payments   │ get_tenants  │ send_notification    │
  └──────────────────────────────────────────────────────┘
```

### Как это работает

**AI-Директор** (оркестратор) — получает вопрос собственника, решает какой агент(ы) вызвать, собирает ответ, форматирует.

### Реализация

LangGraph или кастомный оркестратор на FastAPI с function calling. Каждый агент — это LLM-вызов со своим системным промптом и набором инструментов.

Универсальные CLI-агенты (opencode, hermes и подобные) здесь не подойдут — это инструменты для разработки кода, а не для бизнес-логики. Нужна кастомная система.

## 8. Автоматические сценарии (из п.12 ТЗ)

### Сценарий 1 — окончание договора

90/60/30 дней до окончания:
AI анализирует договор → проверяет рынок → рассчитывает рекомендуемую ставку → создаёт задачу.

### Сценарий 2 — задолженность

Просрочка платежа → уведомление → проверка договора → расчёт задолженности → задача ответственному.

### Сценарий 3 — новый договор

Загрузка договора → AI-анализ → выявление рисков → отчёт → постановка задач.

### Сценарий 4 — новый объект

Добавление объекта → формирование карточки → расчёт показателей → анализ рынка.

### Сценарий 5 — продажа

Поступил потенциальный покупатель → CRM → квалификация → задача → контроль сделки → аналитика.

- Разграничение прав доступа (собственник / сотрудники / риелторы)

- Резервное копирование
- Защита документов
- Контроль доступа к финансовой информации
- Возможность отключения AI-доступа к отдельным данным
- Критически важные действия — только после подтверждения пользователя
